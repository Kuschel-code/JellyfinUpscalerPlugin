# i18n — status, and what is deliberately not done yet

Added in v1.8.3.20 (Phase 2). **No translation happened.** English is the *source*
language: `Configuration/strings.en.json` is where these strings live, not a
translation of them. A locale is added by copying that file, translating the
values, and pointing the loader at it — the UI does not change.

## The mechanism

| Piece | What it does |
|---|---|
| `Configuration/strings.en.json` | The catalogue. Flat `key: string`, no nesting. |
| `Configuration/i18n.js` | `t(key, params)`, `applyTo(root)` for `[data-i18n]`, `ready()`. |
| `Plugin.cs` | Serves both as `UPSCALERStringsEn` / `UPSCALERI18n`. |
| `I18nCatalogueTests` | 7 guards: every used key exists, no empty values, balanced placeholders, both assets embedded *and* registered, the loader asks for the registered route. |

Two properties are deliberate:

- **A missing key renders as the key name**, never as an empty string. A blank
  label is invisible in a screenshot; `strip.autoActive` is not. The test above
  means it should never reach a release anyway.
- **`t()` takes a fallback**: `t('strip.ready', null, 'Ready')`. The catalogue is
  fetched asynchronously, so the first paint would otherwise flash key names.
  The fallback is the literal that used to be inline — deleting it later is a
  one-line change per call site once loading is guaranteed to precede render.

There is no plural handling, no gender, no date formatting. Those are real
problems that need a real library; half of one here would be worse than the
inline strings it replaces. When a second locale needs plurals this gets
swapped — **the call sites will not change**, which is the whole point of doing
the groundwork first.

## What is migrated

The activity strip and the auto-mode surface — the code this release touched:

- strip: running/idle line, phase, frame counters, fps, ETA, relative times,
  job buttons
- auto mode: card headings, live-control labels, the filter suggestion
- player notices

**58 keys.** All of them are new or were rewritten in v1.8.3.20, which is why
this slice was chosen: migrating text nobody is editing risks a regression for
no benefit.

## What is NOT migrated, and why

A full extraction is **~485 strings**:

| Where | Count |
|---|---:|
| `configurationpage.html` text nodes (labels, descriptions, `<option>`s) | ~313 |
| Visible attributes (`title`, `placeholder`, `aria-label`) | 11 |
| Quoted strings across the 7 JS files | ~161 |

Doing that in one pass was rejected, deliberately:

1. **No user-visible benefit until a translation exists**, which is explicitly
   out of scope for this phase.
2. **~485 places to get wrong at once.** `check_ui_field_consistency.py` guards
   element *ids*, not text — a botched extraction ships silently and shows up as
   a blank settings page.
3. The remaining strings are static markup. They need `data-i18n` attributes on
   several hundred elements, which is a mechanical change best done per tab,
   with the page open, rather than as one sweep.

The mechanism handles them already: `applyTo(root)` fills any `[data-i18n]`
element. Nothing needs redesigning to continue — each tab can be migrated on its
own, and the key-coverage test catches a typo the moment it is introduced.

## Adding a locale (once the migration is complete enough to be worth it)

1. `cp Configuration/strings.en.json Configuration/strings.de.json`, translate
   the values, leave the keys alone.
2. Embed it and register a `UPSCALERStringsDe` page in `Plugin.cs`.
3. Pick the file in `i18n.js` `load()` from the Jellyfin user's language.

Step 3 is the only code change, and it is one line.
